# 残迹审计：我怎么验证一个木马到底藏得多深

样本本身总会有人分析，那个不是眼下的事。眼下要回答的是另外三个问题：
它在这儿待了多久，藏到了哪一层，我这套看法有没有可能只是自我安慰。

事故报告的最后一段通常这么写：未发现持久化痕迹。
这句话有两个意思。一个是它不在这儿；另一个是它在这儿，而我们看的方式看不见它。
两句话在纸面上长得一样，在复盘会上代价差得很远。这个项目只做一件事：把它们分开。

## 一、第一次翻车

检查器是我自己写的，第一版就被它骗了。

那套植入物把持久化单元写进 `/etc/systemd/system`，然后把每个文件的 mtime
改到与同目录最新的邻居一致。任何人敲下 `ls -lt`，看到的是一排整齐的老文件。
我写检查器验证这件事，跑出来是 aligned，全部对齐。

它是错的。漏掉的是客户端二进制：它被写进 `/usr/local/bin`，那个目录里原本什么都没有，
对齐代码找不到可以借的时间戳，于是跳过；检查器在同一个目录里也找不到非自家的邻居，
于是拿产物自己当邻居，比完得出「不比邻居新」。

同一次判断，既是识别，又是测量，还是结论。产物给自己做了旁证。

这不是一个 if 写错了。程序说「我把它藏好了」，程序再检查「它藏好了吗」，
程序打印「藏好了」，三段话出自同一套假设，中间没有任何环节允许别人插嘴。

修法是拆：识别（哪些文件算自家的，启发式，必须标注）、测量（mtime、inode、邻居上限，
纯元数据，谁都能重做）、判定（一条可以被别人推翻的判据）。
拆开之后，第一个冒出来的事实是：这个目录里根本没有旁证。
没有旁证的时候，「对齐」不是结论，是假设。工具从那以后在这种目录里返回 partial，
理由写得直白：对齐无法被证明，只能被假设。

## 二、第二次翻车

修完旁证，我以为识别已经干净了。然后在真的 Ubuntu 上跑了一遍。

认领 13 个文件，其中 5 个是我的，8 个不是，精度 38%。
那 8 个是 `/usr/libexec/packagekitd`、`/usr/libexec/boltd`、`/usr/libexec/qmi-proxy`、
`packagekit-direct`、`pk-debconf-helper`、`pk-offline-update`、`mbim-proxy`，
还有 `/etc/cron.d/e2scrub_all`。每一个都由正常安装的 systemd 单元正常启动。

原因很普通：当时的规则是「任何单元的 `ExecStart=` 提到的任何文件都算自家的」。
在一棵只有五个文件的夹具树上，这条规则完美；在一台装了包管理、蓝牙、蜂窝模块的机器上，
它把系统自带二进制一网打尽。夹具太干净，所以规则看起来是对的。

识别层因此改了设计，锚在模式的证据上，而不是锚在「谁提到谁」上：

1. 正文带产物标记（`KillSignal=SIGCONT`、`SendSIGKILL=no`）的单元，算自家的；
2. 这种单元启动的文件，算自家的；
3. 正文提到上述路径的文件，算自家的。这一条抓 cron：它自己没有标记，但一定写它要跑的程序。

同一个 root，认领 5 个，误报 0 个。代价是那 8 个文件变成弱认领，不参与审计。
这个代价没有藏起来，它出现在输出里：`(+8 weak claim(s) not audited)`。
想要旧行为可以加 `--broad`，然后自己承担 38%。

两次翻车的形状一样：判断被当成了测量。第一次是「我认领的文件」被拿去给结论作证；
第二次是「我认领得对不对」这件事本身没有被度量过。两次的修法也一样：
把判断从测量里拆出来，给它一个位置、一个数字、一句「我可能会错」。

## 三、三块地板

想藏起来的东西，能动的是三样：时间、顺序、注意力。三样东西的地板高度不同。

### 时间：mtime 可以借，ctime 不能改

改 mtime 是正常系统调用，`utimensat(2)`，用户态随便调。
读一下邻居的最新 mtime，把自己改成一样，这件事不难。

但改 mtime 这个动作会把文件的 ctime 推到当下。ctime 没有对应的系统调用可以写，
它不是文件的属性，是内核记账的结果。你可以让一个文件声称自己来自 2019 年，
同时无法阻止内核在旁边写下：这个声称发生在今天。

于是 `residue trace` 的第四条检查长这样：

```
trace.ctime   fail   5 artifact(s) have a ctime newer than every sibling:
                     mtime can be borrowed, ctime cannot
```

一次真正干净的投递，需要整个文件系统在同一时刻被构建，也就是做镜像，而不是做投放。

### 顺序：inode 没有系统调用

第二块地板更低。多数 Linux 文件系统单调分配 inode，先写的号小，后写的号大，
用户态没有办法重新编号。能改的只有时间戳、权限、扩展属性，都是 inode 之外的字段。

把目录里所有文件的 inode 排个序，创建顺序就回来了：

```
trace.order   fail   5 artifact(s) have a higher inode than every sibling,
                     so creation order is recoverable
```

这一条几乎不可能通过。它说明的不是检测能力强，而是这一层没有可藏的空间。
把它打印出来，比假装它不存在有用。

### 注意力：分母是最容易被做手脚的地方

前两个问题是「藏不藏得住」，第三个是另一件事：看见了多久。

现实里的报告长这样：该主机自 3 月 12 日起被控，持续 41 天，期间共触发 3 条告警。
这句话里有三个可以随意揉捏的决定。

分母是什么。如果分母是「所有被观察过的主机」，操作者只要多扫、少投，覆盖率就会变好看。
扫一百台、投十台、命中两台，覆盖率 2%，看起来像检测很弱，其实是分母被灌了水。
分母只能是走到投放这一步的主机，只被扫过的主机没有东西可检测。

前置和后置要不要分开。植入物还不存在时规则就响了，那是误报，不是覆盖。
折进同一个比例，检测栈会显得比真实更好，而读者没有办法从那个百分比里看出来。

恰好的 50% 算不算多数。不算。`> 50.0` 才通过，`50.0` 是 partial-coverage，
理由是 exactly half or less is not coverage。没有任何命中数据时是 `unknown, not zero`，
零是测量结果，「我们没看」不是。

这些不是技术难点，是措辞纪律。措辞纪律恰恰是这类报告最容易失守的地方。

## 四、为什么要第二个实现

拆开识别与测量，还剩最后一个口子：测量本身。

于是有了 L3，`tests/cross_check.sh`。做法很土。`residue` 只负责认路径，
从自己的 JSON 输出里把产物路径抠出来；测这一步全部交给 shell 和 `stat(1)`：
取每个文件的 mtime，与同目录所有非产物的 mtime 最大值比一遍，数出几个超了。

```
CROSS_ALIGNED=5   RESIDUE_ALIGNED=5
CROSS_LEAKS=0     RESIDUE_LEAKS=0
CROSS_MATCH=1
```

两个数一致，才算这个测量成立。不一致的时候错的一定有一方，而且不一定是 shell 那一方。

这套东西真正起作用，是在它开始推翻我自己的时候。第一版 trace 说「全部对齐」，
L3 说「六个产物里有一个超了」，超的就是那个客户端二进制。后来发现桥接侧的对齐代码
只在成功时改时间，失败时静默跳过；再后来发现连「成功」的判断本身都是错的，
目录上限里把产物自己算进了邻居。

修完之后我写了一句话进文档：没有 L3，「复算过」等于「同一个程序说了两遍同样的话」。

## 五、地板在哪，为什么不假装它不在

一个测量工具的价值，一半在查得出什么，另一半在写明查不出什么。
`docs/limits.md` 里每一条都会咬人。

目录。创建文件会更新父目录的 mtime，也会更新父目录的 ctime，而 ctime 设不了。
所以一条 `stat /etc/systemd/system` 就能看见目录在 03:14 变过，而里面每个文件都声称来自 2019 年。
这个工具目前没有对目录 ctime 单独开检查。它是最可能在一块人眼一看就脏的主机上返回 pass 的地方，
我把它写在 README 的 Limits 第一段，不等别人发现。

进程。运行中植入物的字符串在内存里，映射发生在挂载之前。
`/proc/<pid>/exe` 背后的二进制即使文件被删掉也仍然可读。
这个工具不读 `/proc` 下的任何东西，所以它能在一台仍然被控的主机上报告一个干净的文件系统。

删除。未链接的 inode 还活在页缓存和日志里。产物在挂载前被删掉，它就从视野里消失。

启发式识别。持久化机制不像 systemd 的植入物（shell profile 里的一行、
一个 `LD_PRELOAD` 条目、一行用 `/bin/sh -c` 内联载荷的 cron）不会被认领，
未被认领的产物根本不会被测量。工具对这类文件的沉默，不算发现。

跨构建相似度。对字符串算 Jaccard 只回答一个问题：两次构建的字符串集合重合度是否超过阈值。
两次构建可以停在 0.90，却依然被控制流形状、函数次序、常量表一眼聚成一类。
低分说明的是这个投影没能把它们分开，不是不可关联的证明。

写清楚这些会削弱工具的说服力。也正是因为写了，它才有说服力：
一个测量工具的价值，在于它能被反对。

## 六、为什么只发怎么测

这个项目是从一套完整攻击链里长出来的：投放、横向、持久化、反取证、命令通道。
那些部分一行都没有放进来，也不会放。

理由不是姿态。仓库里有一套能直接跑起来的投放链，关于测量的讨论就会失去意义，
读者无法区分「这个工具测出来了」和「这个工具的作者知道怎么打」。
审计工具要站在审计方的位置上，它的每一行代码都得能被受害者拿来反对作者。

所以这里只有：一棵能重建的夹具树（五件合成产物，写文本文件然后退出）、
三个只读的判据、一台没有外网且仓库只读挂载的 QEMU 客机、
一个把同一批数字用 `stat(1)` 再算一遍的 shell 脚本，还有一份写明「我查不出什么」的文档。

植入物是合成的，这不是妥协，是必要条件。只有合成植入物，
「它藏得怎么样」才变成一个可以被别人重复的问题。

## 七、三分钟，自己跑一遍

```bash
git clone https://github.com/yaorenliang/residue-audit
cd residue-audit
make demo     # 零依赖，不联网，不需要 root
make verify   # 单测 + L3 交叉复算
make lab      # 真实 ext4 客机，无外网
```

`make demo` 打印三段结论，中间那段是负控：把同一棵树改成「刚刚写入」，
对齐判据必须失败。没有负控的通过，等于没测。

第四段是覆盖率：五台主机，四台走到投放，命中两台，正好 50%。
工具给 partial-coverage，不给 covered。这一行是我在这个仓库里最在意的输出，
它拦下的不是攻击者，是写报告的人。

## 八、结尾

安全报告里最贵的一句话是「未发现」。它听起来像结论，其实是关于观察方法的一句话，
只是没有人把它写全。我想让它变成两句：

> 我们本可以在这一层发现它：文件元数据、创建顺序、目录时间、驻留曲线；
> 我们不可能在那一层发现它：内存、已删除的 inode，以及所有没有交到我们手里的规则。

第一句需要工具，第二句需要诚实。两句话一起，才叫一次审计。
