# 边界

这个工具里每一条检查都有自己的作用域，出了作用域，它的输出不成立。
这份文件就是那条边界，写下来，省得别人靠犯错去发现它。

引用 `residue` 的数字时，请把随附的边界一起引用。

## trace

**它看得见的**：你指向的根目录下已经存在的文件的元数据。就这些。

**它看不见内存。** 运行中植入物的字符串在进程镜像里，映射发生在你挂载之前。这里不读
`/proc/<pid>` 下的任何东西，而 `/proc/<pid>/exe` 背后的二进制即使文件已被删除也仍然可读。
工具会愉快地报告一个干净的文件系统，同时真正要紧的进程还在跑。

**它看不见已删除的文件。** 未链接的 inode 还活在页缓存和日志里。产物在你挂载前被删掉，
它就从视野里消失了，下面所有检查都无从谈起。

**它看得见容纳目录，但只当线索。** 创建文件会更新父目录的 mtime，用户态没有任何技巧能绕开这次写入。
目录也有 ctime，而 ctime 设不了。老练的响应者一条 `stat /etc/systemd/system` 就看见：
目录在 03:14 变过，而里面每个文件都声称来自 2019 年。`trace.directory_ctime` 把这个目录时间
和里面最早的产物比，目录更新就报 `partial`。它停在 partial、不会变成 `fail`，理由很实际：
一次包升级会以同样的顺序碰同一个目录。这条检查定的是**组装**的时间，不是**意图**。

**读不进去的路径是有名有姓的缺口，不是空目录。** 列不出来的目录进 `facts.errors`，
它背后的产物不会被测量，`trace.readable` 降成 `partial`。这条之所以写在这里，是因为它替掉的
失败模式是隐形的：对一个扫描目录 `chmod 000`，从前会产出「没有东西可审」，
对跳过这件事一字不提。`trace.readable` 不是 `pass` 时，下面所有计数描述的树比你以为的小。

**ctime 是「变过」的证据，不是「恶意」的证据。** ctime 无法回溯，所以 ctime 比所有邻居都新的产物
确实是在邻居之后写入的。但「之后」不等于「出自攻击者」：任何重写合法单元文件的进程
（包升级、配置回滚）都会留下同样的信号。ctime 缩小时间窗，不定罪。

**inode 顺序是地板，不是证明。** 多数 Linux 文件系统单调分配 inode，最后创建的文件号通常最大。
两件事让它不那么绝对：删除后的 inode 复用可能把低号给新文件；目录内次序依赖具体文件系统。
此处通过的含义是「没有明显的分配顺序信号」，而不是「创建于邻居之前」。

**识别是启发式的，它的精度是被实测过的。** 一个文件算产物，只有三种情况：
它本身是带正文标记的单元；它被这种单元启动；它的正文提到前两者里的文件。

两个失败方向都真实存在：

* **放宽就会多认。** 第一版规则把「任何单元 ExecStart= 提到的任何文件」都算自家的。
  在标准 Ubuntu 24.04 root 上它认领 13 个、其中 5 个是我们的，精度 38%，
  `packagekitd`、`boltd`、`qmi-proxy` 等 8 个落在误报里。这条规则仍以
  `--broad` 保留，并会打印同样的数字。
* **收窄永远会漏。** 持久化机制不像 systemd 的植入物（shell profile 里的一行、
  `LD_PRELOAD` 条目、用 `/bin/sh -c` 内联载荷的 cron）不会被认领，
  而未被认领的产物根本不会被测量。窄规则拒绝的文件会以 `weak_claims` 计数并报告，
  但**工具对这类文件的沉默，不是一个发现。**

**新鲜度取决于你给的钟。** `--fresh-window` 拿 `time.time()` 比。对一个月前的镜像，
一切都旧，包括入侵。新鲜度用在活主机上，不要用在冷镜像上。

## dwell

**台账是模型，不是记录。** 植入物上了某台机器而事件没写进台账，工具就当它从没被投放，
它算出的每个比例都继承了这个遗漏。输入不全，百分比再精确也没意义。

**覆盖率是「你给的规则」的覆盖率。** `--hits` 是命中事件文件。这个比例回答的是
「在我们投放到的机器里，有多少台至少触发过**这些**命中」。它不是检测栈真实召回率的陈述，
也不可能是，没人把没响的规则交给工具。

**前置/后置依赖时钟一致。** 分界线是每台主机自己的 `deploy` 时间戳。时钟偏斜的主机会把
边界附近的命中分错类。本工具不校时。

**未知事件类型会缩小分母，工具会说出来而不是猜。** 不在 `{deploy, mine, scan}` 里的类型
进 `unknown_events`，并让 `dwell.schema` 报 partial。台账里用了这一版不认识的类型
（`install`、`exploit`、`removed`）时，覆盖率是按它认得的那些主机算的 ——
把 `hit_rate_all_hosts` 读在旁边，并且把 schema partial 读成「这个分母可能是错的」，
而不是「这个比例很低」。

**从未投放过的机器上的命中会被列出来，不参与评分。** 它们进 `hits_unmatched`。
命中一台陌生主机，可能意味着台账缺一行 `deploy`，也可能意味着命中文件是照着另一支舰队生成的；
两种情况它都进不了覆盖率，而静默丢掉它，会让它的规则带着一个不再解释任何东西的计数继续打印。

**跨度量的是存在，不是活动。** 跨度从投放到该主机最后一次事件。没有后续事件不等于植入物停了，
可能只是台账停了。

## batch

**特征是损失信息的投影。** 对提取出的字符串算 Jaccard，只回答一个问题：两次构建的字符串集合
重合度是否超过 98%。两次构建可以坐在 0.90，却依然被控制流形状、函数次序、常量表、段次序
一眼聚成一类，这些本工具一项都不看。

**低分不是不可关联的证据。** 它只说明**这个**投影没能把它们分开。「这两次构建无法被关联」
这个结论需要对分析者可能使用的每一个投影都给出论证，任何一个单独的分数都担不起。

**阈值是约定，不是定律。** 0.98 来自现场的一次复现：同族两次构建停在 0.96 到 0.98，仍然被人手聚成一类。
改阈值就改结论，请说明你用的是哪一个。

**空特征集没有相似度可言。** 两个空集是 `skip`，不是 `fail`：比例本身没有定义，
而报 1.0（旧行为）等于在两次提取都没产出任何东西时声称「两次构建相同」。
一空一非空是真的 0.0，照常评分。

## 退出码

`0` pass、`1` partial、`2` fail、`3` skip、`4` 工具故障。四不是判定：
它表示工具根本没跑成检查（旗标错、输入读不了、崩了）。把 4 当成「发现了东西」的门禁会为一次手滑拉人，
把 4 当成「干净」的门禁更糟。先看退出码，再看摘要行。

## 平台

这些结论在 ext4 上成立。在 APFS 上，目录 mtime 与 inode 分配的行为不同，另有一个字段
（birthtime）本工具不读。在 macOS 主机上跑 `trace` 也会出数，这些数在 Linux 上是否同义，未经验证。
方法文档里的 L2 才是要紧的那道验证：夹具在真实 ext4 客机里跑，无外网，结论与同一套 golden 比对。

## 这个工具是干什么用的

用来把「我们什么都没发现」换成两句话：这是我们本可以发现的那一层，这是我们不可能发现的那一层。
后一句在事故报告里最常被省掉，这份文件就是写它的地方。
